## Fix Plan for OBSINTA-1344

### Version
Plan v2 | Iteration 1 (post-audit revision)

### Root Cause
The `e2e-aws-ovn-conformance-serial` periodic test jobs across all HyperShift release versions (4.14, 4.15, 4.16, 4.17, 4.18, 4.19, 4.20, 4.21, 4.22, 5.0) create guest clusters using the `hypershift-aws-conformance` workflow, which delegates to `hypershift-aws-create` chain. The chain defaults `HYPERSHIFT_INFRA_AVAILABILITY_POLICY` to `SingleReplica`. In this mode, infrastructure services — including the default `IngressController` — are deployed as single-replica pods with no tolerations for `NoExecute` taints. The OpenShift serial conformance test suite (`openshift/conformance/serial`) includes tests that apply `NoExecute` taints to cluster nodes (e.g., node eviction, drain, and taint-based scheduling tests). When such a taint is applied to the node hosting the single ingress controller pod, the pod is evicted without replacement, breaking cluster ingress accessibility and causing cascading test failures.

Note: `main`, `release-4.23`, and `*__hcm/*.mce` periodics do NOT contain `e2e-aws-ovn-conformance-serial` and are correctly excluded from scope. `HYPERSHIFT_CP_AVAILABILITY_POLICY` (control-plane policy) is not changed because the HyperShift control plane runs on the management cluster, not on guest nodes that receive NoExecute taints.

### Approach
Set `HYPERSHIFT_INFRA_AVAILABILITY_POLICY: HighlyAvailable` in the `env` block of each `e2e-aws-ovn-conformance-serial` test definition in the periodics YAML configs for all affected HyperShift release versions. With HighlyAvailable, infrastructure services deploy with multiple replicas spread across nodes. Even if one node receives a `NoExecute` taint, remaining replicas on other nodes maintain ingress availability throughout the test run.

After editing the 10 config files, run `make update` to regenerate all downstream Prow job configurations in `ci-operator/jobs/`. Both the edited config files and the regenerated jobs files must be committed.

This approach is preferred over:
- Skipping taint-related tests (would reduce test coverage without fixing the underlying infra issue)
- Adding tolerations in a pre-test step (more complex, harder to maintain, touches workflow rather than config)
- Changing the workflow default (would affect all tests using hypershift-aws-conformance, not just serial)

### Alternatives Considered
| # | Approach | Pros | Cons | Why Not |
|---|----------|------|------|---------|
| 1 | Add `TEST_SKIPS` for taint-related tests | Simple to implement | Reduces test coverage, doesn't fix underlying infra issue | Hides bug rather than fixing it |
| 2 | Add tolerations to default IngressController via a pre-test step | Fixes ingress pod behavior | More complex, requires new step registry file, harder to maintain | Overkill compared to HA policy change |
| 3 | Change workflow default to HighlyAvailable | Single change point | Affects ALL tests using hypershift-aws-conformance | May introduce resource/cost implications for tests that don't need HA |
| 4 | Patch infra-availability at workflow level | Centralized | Same downside as #3 | Too broad a change |

### Dependencies & Side Effects
- [x] Public API change? No — config-only change to CI test definitions
- [x] Config / env var change? Yes — adds `HYPERSHIFT_INFRA_AVAILABILITY_POLICY: HighlyAvailable` env var to 10 test configs; requires `make update` to propagate to generated jobs
- [x] Database migration? No
- [x] Downstream consumer impact? No downstream consumers of these test configs
- [x] Error handling / logging change? No
- [x] Performance characteristics change? HighlyAvailable clusters require more AWS infrastructure (additional nodes/resources), increasing test cost and slightly longer cluster provisioning time (~5-10 min). Older releases (4.14–4.16) run annually, so cost increase is negligible. Newer releases (4.19–5.0) run daily/weekly.
